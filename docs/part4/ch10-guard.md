## 本章结论

- Guard 不只是 regex 检查，核心是多层检查和不确定性上报。
- ReverseGuard 反向验证 Recipe 引用的 API/符号是否仍存在，是 evolution 的重要证据来源。
- CoverageAnalyzer 和 ComplianceReporter 把单次检查提升为项目级质量报告。
- RuleLearner 用 TP/FP/FN 反馈规则质量，可能触发衰退审查。

## 真实实现链路

- `GuardService` 编排规则召回、文件收集、检查引擎和报告。
- `GuardCheckEngine` 分派 line/code/ast/cross-file 检查。
- `ReverseGuard` 处理 Recipe 到代码符号的反向健康检查。
- `UncertaintyCollector` 记录无法确定的判断，避免误报成确定违规。
- HTTP route 与 MCP handler 只是入口，核心逻辑在 service 层。

## 门控与边界

- 代码模式无法稳定解析时应返回 uncertain。
- Guard 写操作和文件模式检查要经过 Gateway 权限。
- 修复反馈不能直接删除 Recipe，只能成为质量和进化证据。

## 易漂移点

- 检查层数量和名称可能变化，插图需要随 GuardCheckEngine 更新。
- ReverseGuard 与 FileChangeHandler 的证据语义要和 ch07 保持一致。
- Dashboard GuardView 展示字段可能滞后于报告结构。
