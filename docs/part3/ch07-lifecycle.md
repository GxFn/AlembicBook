## 本章结论

- `Lifecycle.ts` 定义六态和合法转移，StateMachine 是状态变化唯一权威。
- `EvolutionGateway.submit()` 的动作只有 `valid`、`update`、`deprecate`：valid 更新 `lastVerifiedAt`，update 创建提案，deprecate 根据 policy 立即执行或创建提案。
- deprecate 立即执行条件是高置信且非 metabolism 来源；Guard 拒绝立即执行时会降级为 Proposal。
- `ProposalExecutor` 订阅 guard、search、decay、quality、usage、lifecycle 信号，只自动评估 observing proposal。
- VSCode extension 只采集文件变化和弹窗，不直接理解 Recipe；未处理变化交给服务端增量扫描和 evolution 统一处理。
- Agent 提交带 suggestedChanges 的 evidence 可以升级已有无变更内容的提案。

## 真实实现链路

- `FileChangeCollector` 合并 IDE rename/save/delete/create、Git HEAD Diff 和 Working Tree Diff，3 秒 flush 到 `/api/v1/file-changes`。
- `file-changes` route 进入 `FileChangeHandler`，由 ContentImpactAnalyzer 和 RecipeImpactPlanner 判断 direct、pattern、related 等影响。
- `KnowledgeRescanPlanner` 和 `EvolutionPrescreen` 在增量扫描阶段筛出需要验证、更新、废弃或交给 Agent 的目标。
- `evolve-external.ts` 把外部 IDE Agent 的 `alembic_evolve` 决策提交到 EvolutionGateway。
- `consolidated.ts` 和 `consolidate.ts` 覆盖提交知识、演化和语义合并的 MCP 尾追溯写入协议。
- `ContentPatcher` 只应用白名单字段和可解析 suggestedChanges，避免 Agent 文本随意覆盖 Recipe。

## 门控与边界

- ProposalRepository 会去重同一 target 和 type 的活跃提案。
- update 提案初始是否 observing 由置信度阈值决定；pending 需要人工、Dashboard 或手动执行推动。
- source_modified 且 direct/pattern 的信号会让 deprecate 提案被视为恢复证据并拒绝。
- ContentPatcher 只能改 coreCode、doClause、dontClause、whenClause、content、sourceRefs、headers 等白名单字段。
- 碎片化或关联 Recipe 过多时，工程逻辑不硬判，应通过 consolidate 或内部 Agent 处理。

## 易漂移点

- 内外部 Agent 的进化入口命名、schema 字段和 handler 参数容易漂移。
- Proposal 状态、观察窗口、阈值和 `expiresAt` 语义已经变化过，必须以代码为准。
- VSCode 文件监听新增信号源时，图解和信号附录都要同步。
- 内部 V2 `knowledge.manage` 和外部 MCP `alembic_evolve` 的字段边界需要持续核查。
